# SITE-12: решение о регистрации и доступе

Дата: 2026-10-21. Документ для решения Максима, не изменение политики. Основание — только снимок `Maverlix777/hub` на `f87e6b1a83721bd6b38d3f56570df28def16b445`. Production, существующие учётные записи и ожидающий патч SITE-3 не проверялись. После интеграции других задач потребуется сверка с новым SHA.

## Что есть в снимке

Worker выдаёт регистрационный challenge без приглашения или одобрения: проверяет имя, ограничения частоты и занятость имени. После успешной проверки passkey создаёт пользователя, credential, entitlement `free` и сессию. Это открытая регистрация с проверками, а не анонимный доступ без аутентификации ([Worker:269–338](https://github.com/Maverlix777/hub/blob/f87e6b1a83721bd6b38d3f56570df28def16b445/src/worker.js#L269-L338)).

В БД есть пользователи, ключи, challenges, сессии и entitlements; `tier` допускает только `free`/`paid`. Полей owner, approval, приглашений нет. Пользовательский идентификатор создаётся случайно; первый пользователь не получает особой роли ([миграция:1–42](https://github.com/Maverlix777/hub/blob/f87e6b1a83721bd6b38d3f56570df28def16b445/migrations/0001_auth.sql#L1-L42), Worker:278).

Сессия загружает tier, `/hub/api/session` возвращает его, но выдача защищённых Assets требует наличия сессии, без проверки entitlement для конкретного приложения ([Worker:197–206](https://github.com/Maverlix777/hub/blob/f87e6b1a83721bd6b38d3f56570df28def16b445/src/worker.js#L197-L206), [262–265](https://github.com/Maverlix777/hub/blob/f87e6b1a83721bd6b38d3f56570df28def16b445/src/worker.js#L262-L265), [461–476](https://github.com/Maverlix777/hub/blob/f87e6b1a83721bd6b38d3f56570df28def16b445/src/worker.js#L461-L476)). Хаб рисует весь APPS, без фильтра прав ([public/hub.js:46–70](https://github.com/Maverlix777/hub/blob/f87e6b1a83721bd6b38d3f56570df28def16b445/public/hub.js#L46-L70)). Экран предлагает создать учётную запись и предупреждает об отсутствии восстановления ([login.html:18–32](https://github.com/Maverlix777/hub/blob/f87e6b1a83721bd6b38d3f56570df28def16b445/public/login.html#L18-L32)). Это описание кода, не доказательство состояния сайта.

## Три варианта

| Вариант | Поведение | Что потребуется |
|---|---|---|
| А. Открытая регистрация + доступ по entitlement | Любой регистрируется, приложения доступны по заданной матрице прав | Серверная матрица ресурсов/операций, проверки Assets/API, фильтр плиток, тесты обхода прямым URL |
| Б. Пригласительные коды | Новый аккаунт создаётся только по действующему приглашению | Таблица приглашений, срок/лимит использования, атомарное погашение, выдача/отзыв, поле формы и тесты повторов |
| В. Первый пользователь — owner, остальные после одобрения | Owner управляет приёмом; новые аккаунты ожидают решения | Отдельные роли и статусы, защищённое администрирование, безопасный bootstrap, миграция, UI ожидания и тесты гонок |

**А — расширение, ещё не реализованное.** Скрытая плитка не защищает файл или API: решение должно приниматься сервером на каждом защищаемом ресурсе. Внешние публичные ссылки из APPS невозможно сделать приватными одним фильтром Hub; нужно явно определить границы управляемых ресурсов. Роль администратора нельзя подменять `paid`. Существующим пользователям потребуется явная политика сохранения либо пересмотра прав, а не молчаливое расширение доступа. Объём: контракт матрицы, серверные проверки, UI и интеграционные тесты разрешённого/запрещённого доступа и истёкших сессий.

**Б** ограничивает приём, но не заменяет права приложений. Приглашение следует связывать с регистрационным процессом и погашать атомарно при успешном создании аккаунта; повтор, гонка и неуспешная проверка passkey не должны открывать второй доступ или расходовать код ошибочно. Нужны правила для уже выданных challenges и существующих аккаунтов. Сырые коды нельзя хранить в git или отчётах. Объём: миграция, операции жизненного цикла приглашения, обе стадии регистрации, UI ошибок и тесты истечения/отзыва/конкуренции.

**В — наиболее сложный организационно.** Нельзя назначать владельца через «кто первым пришёл» на уже работающей базе: её содержимое неизвестно. Для существующего аккаунта требуется отдельно подтверждённое назначение, а не выбор самого раннего `created_at`. Для действительно пустой базы атомарный singleton-bootstrap должен исключить двух владельцев при гонке; сама публичная возможность захватить первое место неприемлема без отдельно согласованного ограничения. Требуются политика pending/approved/rejected, проверка на сервере для старых сессий, отзыв доступа, аудит решений и восстановление управления. Объём: наибольшее число самостоятельных deliverables; никакого безопасного автоматического owner-claim здесь не предлагается.

## Решение и переход

Общий порядок после выбора: определить матрицу доступа и судьбу существующих пользователей, подготовить добавочную миграцию с планом отката, проверить синтетические пустую/непустую базы, гонки и прямой доступ, затем отдельно согласовать применение. Старые credentials и sessions не удалять без явного решения; новый запрет должен действовать на сервере, а не только после перезагрузки страницы. Сроки и часы без оценки конкретной реализации не обещаются.

До решения сохраняется текущее поведение открытой регистрации. Никаких owner-claim, новых ролей, миграций, приглашений, скрытия плиток или изменения production этим документом не выполняется. Контракт доступа в ожидающем production-патче SITE-3 здесь не проверен; его нельзя считать основанием для параллельной правки Worker.
